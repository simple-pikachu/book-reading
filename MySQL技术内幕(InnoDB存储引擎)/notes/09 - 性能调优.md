## 1. 章节定位（约第 383–385 页）

**要点**：

- 调优是分层问题：应用 SQL / schema / 索引 → 引擎参数 → OS / 文件系统 → 存储硬件。
- 书中后半偏**硬件与基准测试**；8.0 时代监控入口应以 **Performance Schema + sys** 为一等公民。
- **不要**再把 Query Cache 当加速器（8.0 已移除）。

**原文**：

> 数据库的性能优化是一个系统性工程，需要从应用程序、数据库本身以及硬件等多个层面进行考虑。

**8.0.34 新写法**：

```sql
-- Query Cache 已不存在；下列应无结果或报错
SHOW VARIABLES LIKE 'query_cache%';

-- 现代监控入口
SELECT * FROM sys.statement_analysis LIMIT 10;
SELECT * FROM sys.schema_table_statistics LIMIT 10;
SELECT * FROM performance_schema.file_summary_by_instance LIMIT 10;
```

## 2. SSD、擦除与读写不对称（约第 385–390 页）

**要点**：

- SSD：**读快、随机写相对贵**；存在擦除块（erase block）粒度，写放大影响寿命与延迟。
- 机械盘时代的「随机 IOPS 极低」叙事在 NVMe 上要重估，但 **写放大 / fsync / 双写** 仍关键。
- InnoDB 的页大小、刷脏、doublewrite 与存储特性互相影响。

**原文**：

> SSD 固态硬盘与传统机械硬盘有着本质不同。SSD 的读操作通常很快，但写操作相对复杂，并且存在擦除块的概念，这导致读写具有不对称性。

**8.0.34 新写法**：

- 生产常见：**云盘（弹性块存储）**、**本地 NVMe**；少见整柜机械盘 RAID 作为唯一方案。
- 关注：
  - `innodb_flush_method`、`innodb_doublewrite`、`innodb_io_capacity(_max)`
  - 云盘 IOPS/吞吐突发额度；本地盘磨损与 RAID 控制器缓存策略
- 页大小：`innodb_page_size` 仍须在实例初始化前决定（与书中一致的「建库前定页大小」纪律）。

```sql
SHOW VARIABLES LIKE 'innodb_page_size';
SHOW VARIABLES LIKE 'innodb_io_capacity%';
SHOW VARIABLES LIKE 'innodb_doublewrite';
SHOW VARIABLES LIKE 'innodb_flush_method';
```

## 3. RAID、Write Back 与控制器工具（约第 390–396 页）

**要点**：

| 级别 | 书中常见评价（方向） |
|------|----------------------|
| RAID5 | 容量好，随机写/重建代价高，数据库写密集场景需谨慎 |
| RAID10 | 性能与冗余较均衡，OLTP 更常见推荐 |
| RAID01 | 与 10 组织方式不同，重建/失效域有差异，勿混称 |

- **Write Back** 缓存：提升写性能，必须有电池/电容保护（BBU），否则掉电丢缓存等于丢提交。
- 书中举例 **MegaCLI** 等厂商工具查看阵列状态与缓存策略。

**原文**：

> 对于数据库应用，通常更推荐使用 RAID 10，而不是 RAID 5。RAID 5 在写密集型负载下可能成为瓶颈，并且在磁盘损坏重建时对性能影响较大。

> 当 RAID 卡启用 Write Back 策略时，需要确保电池备份单元（BBU）工作正常，否则在断电时可能丢失数据。

**8.0.34 新写法**：

- 裸金属：仍可用厂商 CLI（MegaCLI / storcli / ssacli 等）——工具名随代际变化。
- 云主机：多数「RAID」被云盘多副本替代；调优重点转向**云盘类型、队列深度、限流**，而非 MegaCLI。
- 容器/K8s 本地盘：确认是否直通 NVMe、是否被 overlay 放大延迟。

原则仍有效：**有电容的 Write Back 才敢开；否则 Write Through**。

## 4. 基准测试：sysbench 与 TPC-C（约第 396–402 页）

**要点**：

- **sysbench**：通用 CPU/IO/OLTP 脚本，快速看机型与参数量级。
- **TPC-C**：事务型标准负载，接近商业 OLTP，配置与解读更重。
- 基准必须固定：数据量、并发、时长、是否预热、是否持久化（fsync 策略）。

**原文**：

> sysbench 是常用的数据库性能测试工具，可以测试 CPU、I/O 以及 OLTP 场景下的数据库性能。

> TPC-C 是衡量联机交易处理系统性能的基准测试标准之一，常用于评估数据库在 OLTP 场景下的表现。

**8.0.34 新写法**：

```bash
# sysbench 1.x 典型语法（与书中旧 lua/参数名可能不同）
sysbench oltp_read_write \
  --mysql-host=127.0.0.1 --mysql-user=sbtest --mysql-password=xxx \
  --mysql-db=sbtest --tables=10 --table-size=100000 \
  --threads=16 --time=120 --report-interval=10 \
  prepare

sysbench oltp_read_write ... run
sysbench oltp_read_write ... cleanup
```

- 旧书中的 `sysbench --test=oltp` 一类写法已过时；以当前发行版帮助为准。
- 另有 `mysqlslap`、应用侧压测；云上注意邻居噪声与突发积分。

## 5. OLAP vs OLTP 与 Buffer Pool（约第 402–410 页）

**要点**：

| 负载 | 典型瓶颈 | 调优重心 |
|------|----------|----------|
| **OLAP** | 更偏 **CPU**（大扫描、聚合、排序、哈希） | 并行、临时表、列式/分析引擎、避免拖垮 Buffer Pool |
| **OLTP** | 更偏 **IO**（点查/小范围 + 持久化） | Buffer Pool、redo、锁、SQL 索引、连接数 |

- **Buffer Pool 命中率**仍是 InnoDB 核心体温计之一；过低先查是否内存不够、扫描过大、或 BP 被错误挤出。

**原文**：

> 一般而言，OLAP 应用是 CPU 密集型的，而 OLTP 应用是 I/O 密集型的。

> 对于 InnoDB 存储引擎，缓冲池（Buffer Pool）的命中率是衡量性能的重要指标。较高的命中率通常意味着更多的读请求可以在内存中完成。

**8.0.34 新写法**：

```sql
-- 独占机可考虑自动推参（非独占/容器慎用）
SHOW VARIABLES LIKE 'innodb_dedicated_server';
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_buffer_pool_instances';

-- 命中率相关（示意）
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
SELECT * FROM sys.metrics WHERE VARIABLE_NAME LIKE 'innodb_buffer_pool%';

-- 比 SHOW STATUS 更细的等待与 IO
SELECT * FROM sys.io_global_by_wait_by_bytes LIMIT 20;
SELECT * FROM performance_schema.table_io_waits_summary_by_table
ORDER BY SUM_TIMER_WAIT DESC LIMIT 20;
```

**计算命中率（概念）**：

\[
\text{hit ratio} \approx 1 - \frac{\text{Innodb\_buffer\_pool\_reads}}{\text{Innodb\_buffer\_pool\_read\_requests}}
\]

- `innodb_dedicated_server=ON` 时，server 会按物理内存推断 `innodb_buffer_pool_size`、日志容量等——**仅适合机器基本只跑 mysqld**；共享机、K8s limit 场景易过度提交，慎用。
- 监控优先：`performance_schema` + `sys`；`SHOW STATUS` 仅作补充，不要当唯一真相源。

## 6. 参数与监控习惯（本章延伸到 8.0.34）

**仍有效的书中思想**：

- 先找瓶颈（CPU vs IO vs 锁 vs SQL），再调参。
- Buffer Pool 是 InnoDB 内存核心。
- 基准测试要可重复。

**必须换掉的习惯**：

| 旧习惯 | 8.0.34 |
|--------|--------|
| 调 Query Cache / `SQL_CACHE` | **已移除**；缓存放应用或代理 |
| 只看 `SHOW STATUS` | **P_S + sys** |
| 机械盘 RAID 教条照搬云 | 按云盘/NVMe 重新建模 |
| 手写巨大 my.cnf「最优模板」 | 少量关键项 + 压测；可试 `innodb_dedicated_server` |

```sql
-- 快速体检
SELECT VERSION();
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_dedicated_server';
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
SELECT * FROM sys.memory_global_total;
```
