## 1. 事务是什么（约第 285–288 页）

**要点**：

- 事务把数据库从一种**一致状态**转到另一种一致状态；中间状态对外不可见（成功则全可见，失败则全回滚）。
- 「ACID」是理想模型；各厂商实现**不完全同等满足**，需结合隔离级别、宕机恢复、复制语义理解边界。
- InnoDB 默认隔离级别为 **REPEATABLE READ（RR）**，在该默认配置下通常认为满足 ACID 叙事（配合 redo/undo、崩溃恢复）。

**原文**：

> 事务将数据库从一种一致状态转换为另一种一致状态。在数据库提交工作时，可以确保要么所有修改都已保存，要么所有修改都不保存。

> 数据库事务正确执行需满足 ACID 特性，即原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）和持久性（Durability）。需要注意的是，并不是所有数据库厂商都完全满足 ACID。

> InnoDB 存储引擎默认的事务隔离级别为 REPEATABLE READ，在该隔离级别下 InnoDB 满足 ACID 特性。

**8.0.34 新写法**：

```sql
SELECT VERSION();  -- 期望 8.0.34
SELECT @@transaction_isolation, @@transaction_read_only;
-- 过时：SELECT @@tx_isolation;  （8.0 已移除/不可用）

-- 会话级修改隔离级别（勿再写 SET tx_isolation）
SET SESSION transaction_isolation = 'REPEATABLE-READ';
SET SESSION transaction_isolation = 'READ-COMMITTED';

SHOW VARIABLES LIKE 'transaction_%';
```

- 配置文件中用 `transaction-isolation` / `transaction-read-only`，不要写旧名 `tx_isolation`。
- 「默认 RR + ACID」在 8.0 仍大体成立；生产若改 RC，需重新评估幻读/间隙锁/复制场景。

## 2. redo 与 undo：谁保证什么（约第 289–300 页）

**要点**：

| 日志 | 主要保证 | 日志形态 | 常见误解 |
|------|----------|----------|----------|
| **redo** | **原子性 + 持久性**（崩溃后可重做已提交修改） | 多为**物理**日志（页级改动） | 「redo 是 undo 的逆运算」——**不是** |
| **undo** | **一致性**（回滚未提交变更；并为 MVCC 提供历史版本） | **逻辑**日志（反向操作） | 「undo 把页物理还原」——一般是**逻辑回滚** |

- redo 在事务执行过程中**不断写入**（先于数据页刷盘的设计目标）；binlog 通常在事务**提交阶段**按事件写入（与引擎内部两阶段配合）。
- redo / undo **不是互逆**：二者职责、格式、刷盘时机都不同，不能把一方当成另一方的「反向拷贝」。

**原文**：

> redo log 用来保证事务的原子性和持久性；undo log 用来保证事务的一致性。

> redo log 基本上都是物理日志，记录的是对每个页的修改；undo log 是逻辑日志，根据每行记录进行记录。

> redo 和 undo 并不是互逆的操作。redo 是用来保证事务的原子性和持久性，undo 是用来保证事务的一致性。

> 二进制日志（binlog）只在事务提交完成后进行一次写入，而 redo log 在事务进行过程中不断地写入。

**8.0.34 新写法**：

```sql
-- redo 容量（≥8.0.30 优先；8.0.34 适用）
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
-- 旧：innodb_log_file_size / innodb_log_files_in_group（≥8.0.30 弃用路径）

SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';  -- 1=每次提交刷 redo（最安全）
SHOW VARIABLES LIKE 'sync_binlog';                     -- 1=每次提交刷 binlog

-- 观察 undo / history
SHOW VARIABLES LIKE 'innodb_undo%';
SELECT NAME, SPACE, STATE FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE '%undo%' OR SPACE_TYPE LIKE '%Undo%';
```

- 独立 undo 表空间 + 在线收缩/截断能力比 5.6 书中叙事更完整（见下节）。
- 内部两阶段：InnoDB（引擎）与 binlog（server）通过 **内部 XA** 保证崩溃后要么都提交要么都回滚——`innodb_support_xa` **已移除，始终开启**，不要再尝试关闭。

## 3. undo、MVCC、purge 与 History list（约第 300–315 页）

**要点**：

- 回滚时按 undo **逻辑反向操作**（如 INSERT 的 undo 是 DELETE），而不是把数据页「拷贝还原」。
- **MVCC** 依赖 undo 中的历史版本构造一致性读视图。
- **purge** 清理已不再被任何活跃事务需要的 undo；清理不及时会导致 undo 膨胀。
- undo 页可**重用**；监控常看 **History list length**（过长 = 长事务 / purge 跟不上 / 大批量变更）。

**原文**：

> undo 是逻辑日志，因此只是将数据库逻辑地恢复到原来的样子，而不是从物理页上做恢复。

> 多版本并发控制（MVCC）的实现也是通过 undo。当用户读取一行记录时，若该记录已被其他事务占用，当前事务可以通过 undo 读取之前的行版本信息，以此实现非锁定读。

> purge 用于最终删除那些不再需要的 undo 页与标记删除的记录。若 History list length 持续增长，通常意味着存在长事务或 purge 跟不上写入速度。

**8.0.34 新写法**：

```sql
-- History list / 相关指标（8.0 常用）
SHOW ENGINE INNODB STATUS\G
-- 在 TRANSACTIONS 段查看 History list length

SELECT * FROM sys.metrics
WHERE VARIABLE_NAME LIKE '%history%' OR VARIABLE_NAME LIKE '%purge%';

-- 独立 undo 表空间（8.0）
CREATE UNDO TABLESPACE undo_003 ADD DATAFILE 'undo_003.ibu';
ALTER UNDO TABLESPACE undo_003 SET INACTIVE;  -- 再 truncate（按手册流程）
-- DROP UNDO TABLESPACE ...

SHOW VARIABLES LIKE 'innodb_undo_tablespaces';
SHOW VARIABLES LIKE 'innodb_max_undo_log_size';
SHOW VARIABLES LIKE 'innodb_purge_threads';
```

- 长事务是 History list 膨胀的头号工程原因：尽量 **mini-batch** 提交，避免一个事务扫改数小时。
- 8.0 可用独立 undo tablespace 做空间回收，比书中「共享系统表空间里塞 undo」时代更好运维。

## 4. 事务提交、group commit、completion_type（约第 315–325 页）

**要点**：

- **group commit**：多个事务的日志刷盘可合并，降低 fsync 次数，提升吞吐。
- `completion_type` 等会话选项影响 COMMIT/ROLLBACK 后连接是否自动开启新事务等行为（以现行手册为准，少见场景再动）。
- **TRUNCATE TABLE** 在 MySQL 中按 **DDL** 处理：**不可回滚**（与「DELETE 全部行」语义不同）。

**原文**：

> InnoDB 存储引擎通过 group commit 的方式，将多个事务的写入操作合并，从而减少磁盘的同步次数，提高数据库的性能。

> TRUNCATE TABLE 操作被映射为 DDL 操作，因此操作不可回滚；若需要可回滚的清空，应使用 DELETE。

**8.0.34 新写法**：

```sql
SHOW VARIABLES LIKE 'binlog_group_commit_sync%';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'completion_type';

-- 原子 DDL（8.0）：多数 DDL 在崩溃场景下要么完成要么回滚，降低「半成品元数据」
-- 但 TRUNCATE 仍不是「事务内可 ROLLBACK 的 DML」
START TRANSACTION;
TRUNCATE TABLE t;   -- 隐式提交 / 不可当普通 DML 回滚
ROLLBACK;           -- 无法撤销已发生的 TRUNCATE
```

- 8.0 **原子 DDL** + 事务型数据字典：运维上比 5.6 的 `.frm` 半更新故事更安全，但**不要**因此把 TRUNCATE 当成可回滚删除。
- Group Replication / 半同步等会改变「提交可见性」与延迟模型，调优时不要只盯单机 group commit。

## 5. 隔离级别、锁与 SERIALIZABLE（约第 325–335 页）

**要点**：

- 隔离级别与锁策略强相关：RR 下 InnoDB 常用 Next-Key 抑制幻读；RC 下间隙锁行为更弱、更依赖行锁。
- **SERIALIZABLE**：强制更多锁定读语义；书中指出多见于**分布式**场景需求，单机 OLTP 较少默认使用。
- 分布式事务：**XA**（外部）+ **内部 XA**（binlog ↔ InnoDB）。

**原文**：

> 隔离级别越低，事务请求的锁越少或持锁时间越短，并发度通常越高，但异常现象也更易出现。

> SERIALIZABLE 隔离级别一般用于分布式数据库场景。对于 InnoDB 存储引擎，在绝大多数情况下使用默认的 REPEATABLE READ 即可。

> 为了保证 InnoDB 存储引擎中的事务与二进制日志中的事务一致，MySQL 使用了内部 XA 事务，即使在关闭 `innodb_support_xa` 时，内部 XA 依然需要。

**8.0.34 新写法**：

```sql
-- 唯一正确的隔离级别变量名
SET SESSION transaction_isolation = 'SERIALIZABLE';
SELECT @@transaction_isolation;

-- 锁观察（勿再用 INNODB_LOCKS）
SELECT * FROM performance_schema.data_locks LIMIT 20;
SELECT * FROM performance_schema.data_lock_waits LIMIT 20;
SELECT * FROM sys.innodb_lock_waits;

-- XA 仍可用；innodb_support_xa 已移除（始终支持）
XA START 'xid1';
-- ... DML ...
XA END 'xid1';
XA PREPARE 'xid1';
XA COMMIT 'xid1';
```

- 高可用拓扑优先学 **Group Replication / InnoDB Cluster / GTID**，不要只停在书中早期 XA 示例。
- 账户与权限变更请用 `CREATE USER` / `ALTER USER`，**不要用 `PASSWORD()`**（已移除）。

```sql
-- 过时
-- SET PASSWORD = PASSWORD('secret');

-- 8.0.34
CREATE USER 'app'@'%' IDENTIFIED BY 'secret';
ALTER USER 'app'@'%' IDENTIFIED BY 'new_secret';
```

## 6. 坏习惯与工程实践（约第 335–349 页）

**要点**：

1. **循环里频繁 COMMIT**：放大 fsync / 组提交收益被打散，吞吐与延迟双损。
2. **自动提交差异**：C API、命令行、Python 驱动等对 `autocommit` 默认值与「隐式事务」行为不一致——写客户端前先确认。
3. **长事务**：改为 **mini-batch**（按主键区间/时间窗分批提交），控制 undo、锁持有时间与主从延迟。

**原文**：

> 一个不好的习惯是在循环中进行事务的提交。这样会破坏 InnoDB 存储引擎的 group commit 特性，导致性能下降。

> 需要注意不同 API 下自动提交的差异。例如，MySQL C API 默认自动提交为开启，而某些语言的连接库可能默认关闭自动提交，开发者应显式控制事务边界。

> 对于长事务，一个较好的方法是将其拆分为多个小事务（mini batch）进行处理。

**8.0.34 新写法**：

```sql
-- 明确事务边界（推荐）
SET SESSION autocommit = 0;
START TRANSACTION;
-- ... 一批合理大小的 DML ...
COMMIT;

-- 或
SET SESSION autocommit = 1;  -- 单语句事务；批量写入时改为显式事务

-- 找长事务（8.0）
SELECT * FROM sys.session WHERE trx_state = 'RUNNING';
SELECT * FROM information_schema.INNODB_TRX
ORDER BY trx_started ASC LIMIT 20;
```

**实践清单（仍完全有效）**：

- 禁止「每行一次 COMMIT」的热循环。
- ORM 默认 autocommit / 连接池复用会话时，检查隔离级别与未提交事务是否泄漏。
- 批处理：控制每批行数、重试幂等、记录断点；监控 History list length 与副本延迟。
