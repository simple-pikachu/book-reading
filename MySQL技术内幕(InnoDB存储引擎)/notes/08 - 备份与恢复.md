## 1. 备份目标与分类（约第 350–355 页）

**要点**：

- 备份是为了**可恢复**：先定义 RPO/RTO，再选工具。
- 两大类：
  - **逻辑备份**：导出 SQL / 文本（如 `mysqldump`、`SELECT ... INTO OUTFILE`），可移植、慢、易跨版本。
  - **裸文件 / 物理备份**：拷贝表空间与 redo 等（热备工具或冷备停机拷贝），恢复快、体积大、版本绑定更强。
- 官方叙事长期强调：MySQL **没有**像某些商业库那样「引擎内置真正增量备份」的一等公民；增量常靠 **binlog**、或第三方物理增量。
- **异地容灾**：备份副本异地存放；复制拓扑跨机房，防单站点灾难。

**原文**：

> 备份可以分为逻辑备份和裸文件备份。逻辑备份是将数据库中的数据导出为文本文件；裸文件备份则是对数据库的物理文件进行备份。

> MySQL 数据库本身并没有提供真正意义上的增量备份方法。增量备份可以通过二进制日志来完成。

> 对于重要的应用，不仅需要备份，还需要考虑异地容灾，以防止机房级别的故障。

**8.0.34 新写法**：

| 场景 | 推荐路径（8.0.34） |
|------|-------------------|
| 逻辑全备 / 逻辑导出 | `mysqldump`、`mysqlpump`、`mydumper`；注意 GTID |
| 物理热备（开源） | **Percona XtraBackup 8.0**（必须与 server 大版本匹配） |
| 物理热备（商业） | **MySQL Enterprise Backup（MEB）** |
| 实例级快速克隆 | **Clone Plugin**（本地/远程克隆） |
| 时间点恢复（PITR） | 物理/逻辑基线 + **二进制日志 + GTID** |

```sql
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'gtid_mode';
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'secure_file_priv';
```

- **勿再依赖 `.frm` 冷备清单**：8.0 元数据在事务型 Data Dictionary（如 `mysql.ibd`），冷备必须按「整实例文件集合 + redo」一致性方式，而不是「表文件 + .frm」旧配方。

## 2. 逻辑备份实践（约第 355–362 页）

**要点**：

- `mysqldump`：一致性需 `--single-transaction`（InnoDB）等；锁表类选项对大库不友好。
- `SELECT ... INTO OUTFILE` / `LOAD DATA`：适合单表批量，受 `secure_file_priv` 限制。
- 恢复时注意字符集、对象顺序（视图/触发器/例程）、权限账户（8.0 账户语句事务性）。

**原文**：

> mysqldump 是 MySQL 官方提供的逻辑备份工具。对于 InnoDB 表，可以通过 --single-transaction 选项获得一致性备份，而不需要对表进行加锁。

> SELECT ... INTO OUTFILE 可以将表中的数据导出到文本文件，之后通过 LOAD DATA INFILE 进行导入。

**8.0.34 新写法**：

```bash
# 逻辑备份（GTID 环境注意 set-gtid-purged）
mysqldump --single-transaction --routines --triggers --events \
  --set-gtid-purged=ON \
  -u root -p --all-databases > full.sql

# 若导入到非 GTID 实例，可按需：
# --set-gtid-purged=OFF

# 恢复
mysql -u root -p < full.sql
```

```sql
-- OUTFILE 仍可用，但路径受控
SHOW VARIABLES LIKE 'secure_file_priv';
SELECT * FROM db.t INTO OUTFILE '/var/lib/mysql-files/t.csv'
FIELDS TERMINATED BY ',' ENCLOSED BY '"';
```

- 大实例逻辑备份往往只做结构 + 小表；大数据用物理备份。
- 导入前确认目标是 8.0.34 兼容的 sql_mode / 字符集（默认 `utf8mb4`）。

## 3. 物理备份：ibbackup / xtrabackup（约第 362–370 页）

**要点**：

- 书中重点介绍 **ibbackup**（InnoDB Hot Backup 商业线）以及社区常用的 **xtrabackup** 思路：拷贝文件 + 应用 redo 得到一致性。
- 冷备：停库拷贝数据目录——简单但停机。
- 热备：在线拷贝 + redo 追平。

**原文**：

> InnoDB Hot Backup（ibbackup）可以对 InnoDB 表进行热备份，备份过程中不需要锁表，也不影响数据库的正常读写。

> Percona 公司的 XtraBackup 是开源的热备工具，其实现思想与 InnoDB Hot Backup 类似。

**8.0.34 新写法**：

| 书中 | 8.0.34 |
|------|--------|
| ibbackup | 产品线演进为 **MySQL Enterprise Backup（MEB）** |
| xtrabackup（5.x） | 必须用 **XtraBackup 8.0.x**，与 8.0.34 匹配；勿用 2.4 备 8.0 |
| （无） | **CLONE PLUGIN**：`CLONE INSTANCE FROM ...` / 本地克隆 |

```sql
-- Clone Plugin（示例思路）
INSTALL PLUGIN clone SONAME 'mysql_clone.so';  -- 若未默认加载
SET GLOBAL clone_valid_donor_list = 'donor.host:3306';
CLONE INSTANCE FROM 'user'@'donor.host':3306 IDENTIFIED BY 'pwd';
```

```bash
# XtraBackup 8.0 典型流程（示意）
xtrabackup --backup --target-dir=/data/backup/full
xtrabackup --prepare --target-dir=/data/backup/full
# 恢复：停库、替换数据目录、启动（按官方文档）
```

- 物理备份后做 **PITR**：保留备份点之后的 binlog，用 `mysqlbinlog` 按时间或 GTID 重放。
- **mysql_upgrade**：≥ **8.0.16** 起由 server 启动自动升级（`--upgrade`），日常恢复后**不必**再手跑 `mysql_upgrade`（除非手册特例）。

## 4. 复制作为「准实时备份」与防误操作（约第 370–378 页）

**要点**：

- 复制三步骤（经典异步）：
  1. 主库事务提交并写入 binlog；
  2. 从库 IO 线程拉取并写入 relay log；
  3. 从库 SQL 线程重放 relay log。
- 运维观察：书中 `SHOW MASTER STATUS` / `SHOW SLAVE STATUS`。
- **快照 + 复制**：用只读副本或延时副本降低误 `DELETE`/`DROP` 的爆炸半径。
- **延时复制**：`CHANGE MASTER TO MASTER_DELAY = N`，提供后悔窗口。
- **read-only**：从库设只读，防止误写。

**原文**：

> MySQL 数据库的复制是通过三个步骤来完成的：主服务器将更新写入二进制日志；从服务器将主服务器的二进制日志复制到本地的中继日志；从服务器重做中继日志中的事件。

> 通过 SHOW MASTER STATUS 和 SHOW SLAVE STATUS 可以观察复制的进度与状态。

> 延时复制可以让从服务器落后主服务器一段时间，从而在误操作发生后仍有机会从从服务器恢复数据。

> 建议将从服务器设置为 read-only，以避免在从服务器上进行误写操作。

**8.0.34 新写法**：

```sql
-- 术语：replica（SLAVE 相关语句多已弃用但仍可能兼容）
SHOW BINARY LOG STATUS;          -- 替代 SHOW MASTER STATUS（8.0.22+ 推荐）
SHOW REPLICA STATUS\G            -- 替代 SHOW SLAVE STATUS

-- 只读
SET GLOBAL read_only = ON;
SET GLOBAL super_read_only = ON;  -- 连 SUPER 也挡（运维账号需规划）

-- 延时复制（8.0 语法示意）
CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 3600;  -- 秒
START REPLICA;

-- GTID
SHOW VARIABLES LIKE 'gtid_mode';
SHOW VARIABLES LIKE 'enforce_gtid_consistency';
SELECT @@GLOBAL.GTID_EXECUTED;
```

```bash
# PITR 示意：从位点/GTID 重放
mysqlbinlog --start-datetime="2026-07-24 10:00:00" \
  --stop-datetime="2026-07-24 11:00:00" binlog.000123 | mysql -u root -p
```

- **Group Replication**：多主/单主组成员、多数派、自动成员管理——书中传统异步主从未覆盖，8.0.34 生产高可用常走这条线或 InnoDB Cluster。
- 副本**不是**备份：仍需独立物理/逻辑备份介质；副本可被错误 DDL/DML 同样毁掉（除非延时 + 及时切换）。

## 5. 恢复演练与清单（约第 378–382 页）

**要点**：

- 定期做**恢复演练**，否则备份等于安慰剂。
- 记录：备份时间、binlog 位点 / GTID、工具版本、校验和。
- 异地：至少一份离线、离站点副本。

**原文**：

> 备份策略制定后，还必须定期进行恢复测试，以确保在真正需要时能够成功恢复。

**8.0.34 新写法（检查清单）**：

1. `SELECT VERSION();` 确认工具链与实例同属 8.0.34 一代。  
2. 物理备份工具版本匹配（XtraBackup 8.0 / MEB 对应版本 / Clone）。  
3. GTID 开启时 `mysqldump --set-gtid-purged` 策略与目标实例一致。  
4. 恢复后验证：表行数抽样、校验和应用只读流量、复制延迟、`GTID_EXECUTED`。  
5. 不要手跑过时的 `mysql_upgrade`（除非文档明确要求）。  
6. 冷备清单**不要**再列 `.frm` / `.par` 为元数据必需项。
